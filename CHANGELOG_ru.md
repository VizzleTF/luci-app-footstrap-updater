Значимые изменения `luci-app-footstrap-updater`, новое сверху. Формат —
[Keep a Changelog](https://keepachangelog.com/1.1.0/); коммиты —
[Conventional Commits](https://www.conventionalcommits.org/), версии —
[SemVer](https://semver.org/). Секции в фиксированном порядке: Добавлено, Изменено,
Устарело, Удалено, Исправлено, Безопасность, Производительность — по одной на выпуск.

## [Unreleased]

### Добавлено

- **Необязательный `GITHUB_PROXY`, читаемый из UCI.** Для сетей, где GitHub недоступен вовсе. `uci set footstrap.settings.github_proxy=https://ваш-прокси/` подставляет префикс к github-адресам, пробуется первым, прямой путь — запасной. Из окружения не читается никогда: rpcd передаёт этому бэкенду окружение вызывающего, так что прокси из env позволил бы любому с ACL обновления направить загрузку под root на произвольный хост; `GITHUB_PROXY` добавлен в список unset рядом с `http_proxy`. Безопасно, потому что манифест подписан, а каждый пакет сверяется с ним по хешу.

- **Подписанный манифест релиза вытеснил `api.github.com` из всего пакета.** `check`, `check-updater`, `notes`, проверка свободного места и сама установка читают `manifest.txt` + `manifest.txt.sig` с `releases/latest/download/` — с CDN релизов, у которого лимита запросов нет. REST API даёт **60 неаутентифицированных запросов в час на IP источника**, а этот бэкенд спрашивал на каждом `check`, то есть за бейджем обновления при загрузке страницы: за CGNAT или общим выходом лимит кончался раньше, чем админ успевал что-то нажать, и все пути умирали с `ERR: cannot reach the GitHub release API` (issue #17 темы). Замерено: API отвечает `x-ratelimit-limit: 60`, а `releases/latest/download/…` — 302 вообще без заголовков `x-ratelimit-*`.

- **Зеркало релиза на GitHub Pages — с манифестом и пакетами.** Второй хост для роутера, которому `github.com` недоступен совсем; пакеты там обязательны, потому что URL ассета редиректит *через* `github.com`. Доверия не требует: манифест подписан, пакеты сверяются с ним по хешу, так что зеркало может отдать настоящий релиз либо не отдать ничего. Откуда пришёл манифест, записывается рядом с ним на диск: `check` кэширует манифест, а поздний `notes` читает его уже в другом процессе — в переменной источник терялся на этой границе, и роутер на зеркале молча уходил за notes и пакетом обратно на `github.com`.

### Изменено

- **Пакет теперь накрыт одной проверкой подписи вместо двух проверок против разных противников.** sha256 брался из `@.assets[*].digest`, который GitHub считает по загруженным байтам — подменил ассет, и digest пересчитали за тебя, — поэтому рядом жила ed25519-подпись каждого пакета. Хеш переехал в подписанный манифест: одна проверка манифеста накрывает все перечисленные пакеты, отдельный `.sig` не скачивается. На один запрос меньше и строго более сильная проверка.

- **Release notes в диалоге подтверждения и проверка места стали подписанными данными.** Notes были `@.body` — текстом, который никто не проверял, — а preflight мерил установку под root по неподписанному `@.assets[*].size`. Теперь notes это ассет `notes.md`, чей sha256 несёт манифест (при несовпадении просто не показываются — верно для косметической строки), а размеры берутся из манифеста.

- **TTL кэша больше не лимитный бюджет.** 300 с остаются, но ради CDN, а не ради экономии 60 вызовов в час.

### Удалено

- **Откат, который выбирал этот пакет из релиза ТЕМЫ, и обслуживавший его `asset_ver()`.** Он существовал ровно для одной ситуации — у этого репозитория ещё не было релиза, — и она закончилась с выходом v1.0.0. Держать его дальше значило держать никем не исполняемый путь и хелпер, чья единственная задача — вытащить версию из имени файла, потому что тег релиза темы это версия темы.

### Исправлено

- **Повторно подсунутый манифест больше не понижает версию темы.** Подписанный манифест валиден вечно, поэтому старый — с устаревшего зеркала или из кэша — поставил бы более старую тему поверх новой, и все проверки бы прошли. Строго более старая версия отклоняется; равная ставится, потому что это осознанная переустановка кнопкой Update.

- **Манифест, называющий другой репозиторий, отклоняется.** Один ключ подписывает манифесты обоих репозиториев, так что без этой проверки манифест темы идеально прошёл бы как манифест этого пакета.

## [1.0.0] — 2026-07-22

### Добавлено

- **Бэкенд самообновления и UI обновления в Appearance теперь живут в своём репозитории, со своими
  тегами и релизным потоком, независимо от темы.** Выделено из `VizzleTF/luci-theme-footstrap`, где
  оба пакета делили одну версию и один релиз. Апдейтер теперь версионируется сам: `fs-update.js` несёт
  `UPD_VERSION` (штампуется из тегов этого репо), а self-updater сравнивает установленную версию с
  последним тегом этого репо — так неизменный апдейтер не скачивается и не переустанавливается
  («использовать существующий»). Релиз, затрагивающий только тему, больше не перевыпускает апдейтер,
  и наоборот.
- **Self-updater резолвит тему и апдейтер из двух репозиториев и ставит оба одной кнопкой.**
  `do_update` ходит к двум release-API — тема из `luci-theme-footstrap`, апдейтер из
  `luci-app-footstrap-updater` — проверяет каждый одним ключом релиза и пропускает апдейтер, если он
  уже актуален. Бейдж в Appearance загорается для обновления темы ИЛИ апдейтера (`check` +
  `check-updater`), а диалог подтверждения показывает шаг версий для каждого отставшего пакета.
- **Обновление в один клик показывает примечания к выпуску, шаг версий и предупреждение о несовместимых
  изменениях до установки** (перенесено из темы). Примечания рендерятся как текстовый узел (показаны до
  проверки подписи), цветной баннер появляется, когда выпуск помечает заголовок `### Removed`/`###
  Security` или слово «breaking».
- **Предполётная проверка места отклоняет обновление, которое не поместится, ещё до первого байта**
  (перенесено). Суммирует размеры ассетов из API и проверяет tmpfs загрузки и overlay распаковки;
  отказывает в открытую, ведь место не является свойством безопасности.

### Изменено

- **Апдейтер ищет себя сначала в этом репозитории и откатывается на релиз темы, пока этому
  репозиторию нечего предложить.** Один резолвер (`resolve_updater()`) отвечает на вопрос «откуда
  берётся апдейтер», и через него идут и установка, и бейдж — иначе бейдж читает один источник, а
  установка другой, и он либо предлагает обновление, которого не будет, либо прячет то, которое есть.
  Этот репозиторий выигрывает всегда, когда публикует ассет, независимо от версий, — так что день его
  первого релиза и есть день переезда всех роутеров, без второго решения где-либо. До тех пор
  транзишн-релиз темы везёт подписанный ассет апдейтера, и ставится именно он: оба источника
  проверяются одним и тем же ed25519-ключом, так что фолбэк меняет, откуда приходят байты, но не то,
  проверяются ли они. На запасном пути версия берётся из ИМЕНИ файла (`asset_ver()`, обе схемы —
  apk и ipk): `tag_name` релиза темы — это версия темы, а не этого пакета.
  **Первый тег этого репозитория обязан быть выше версии транзишн-сборки**: opkg по умолчанию
  отказывается от даунгрейда («Not downgrading package …»), выходит с кодом 0 и не ставит ничего — тег
  ниже запер бы каждый роутер на 24.10 на транзишн-сборке, отчитавшись об успехе.
- **`$EXT` вычисляется один раз на верхнем уровне, а не внутри `do_update`.** `check-updater` теперь
  тоже резолвит ассет, а с пустым `$EXT` `asset_urls` искал имя, оканчивающееся голой точкой, — то
  есть не находил ничего: молчаливое «обновлений нет» на каждом роутере.

### Исправлено

- **Провал обновления самого апдейтера больше не докладывается как провал всего обновления, когда тема
  уже установлена** (перенесено). `fetch_verify_install` при провале проверки не ставит ничего, так что
  старый апдейтер остаётся цел для повтора, а прогон финализируется (сброс кэшей, `OK`, перезагрузка
  клиента), раз тема встала.
